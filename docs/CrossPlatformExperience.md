# Deskflow 跨系统工作台产品与技术设计

实现已加入共享工作台模块。当前支持范围、安装方法与使用步骤见 [共享工作台使用说明](WorkspaceGuide.zh-CN.md)。以下章节保留初始产品方案与性能目标；生产音频采用独立 TLS 通道上的 PCM，文件和声音运行于登录用户的 GUI 进程，键鼠 core 仅接收经过本机身份验证的显示器拓扑。

面向 Windows 提供键鼠、macOS 接收输入的常用场景，同时为双向文件传输、多显示器和其他系统保留扩展空间。产品目标是让用户在自己的多台电脑之间自然工作：输入遵循目标设备的习惯，切换服从用户意图，声音和文件拥有独立、可预期的去向。

保留现有 C++20、Qt6 和平台原生适配层。先完善输入体验与连接正确性，再扩展独立的数据通道与显示器拓扑。无需为了界面换一套语言或重写全部输入核心。

## 产品边界与默认行为

“服务端”和“客户端”描述连接方式，不能代替每项资源的方向。界面应直接显示“这套键鼠控制哪台电脑”“哪台电脑的声音播放到哪里”“文件正在发给谁”。Windows 可以一直是输入来源，Mac 可以一直是音频接收端；鼠标返回 Windows 不应打断 Mac 上的音乐或文件传输。

| 能力 | 推荐新用户体验 | 保留的选择 |
| --- | --- | --- |
| 键盘 | 按目标系统使用输入法，提供可见的键盘配置 | 原样透传、目标系统习惯、自定义按键 |
| 跨屏 | 普通工作自然穿越；保护模式阻止无意越界 | 停留切换、双碰边缘、按住修饰键切换、快捷键直达 |
| 游戏与全屏 | 清楚显示锁定原因，允许快捷键主动切换 | 按应用规则、全部全屏窗口保护、临时放行 |
| 音频 | 用户启用后固定 Windows 输出到所选 Mac 输出 | 本机与远端同时播放、可选跟随输入焦点 |
| 文件 | 双向复制文件及文件夹，有进度和取消入口 | 原生复制粘贴、传输栏、后续跨桌面拖放 |
| 显示器 | 自动识别并单独摆放每块显示器 | 简单电脑视图、每屏自由画布、边缘连接编辑 |

现有用户升级时保留原设置。新的输入法与全屏保护选项先显式启用；完整的新用户向导可以在经过联机验收后应用推荐配置。

首页应包含设备与显示器布局、当前输入目标、固定音频路由、传输进度，以及一键锁定入口。状态变化只做短提示；长时间锁定或传输错误在托盘和首页持续可见，避免用户猜测鼠标为什么不能过去。

连接在本地网络内完成，沿用现有设备信任关系。附加数据连接必须绑定已经认证的设备会话，不能仅凭同网段地址取得音频或文件。

## 五个痛点的源码结论

以下基线来自开始本轮改造前的 `f22c5f18b`，不是对上游所有版本的概括。

| 痛点 | 已有机制与限制 | 对改造的影响 |
| --- | --- | --- |
| Mac Caps Lock | `OSXKeyState.cpp` 把 Caps 当锁定修饰键注入；客户端已有服务端语言同步选项 | 需要同时处理输入源动作、锁定位和受 Caps 影响的字符 |
| 游戏误穿屏 | `Server.cpp` 已有手动锁定、延迟和双碰边缘；Windows 离开检查没有全屏策略 | 复用边缘切换入口，自动保护与手动锁定分别维护 |
| 声音 | `ClientProxy1_9.cpp` 生成 440 Hz 正弦；没有系统输出采集 | 原型修复不能算完成系统声音共享 |
| 文件 | `IClipboard` 只有文字、HTML、位图；1.5 的拖放与文件接口为空 | 需要原生文件表示、真正的传输服务和目标应用适配 |
| 多显示器 | Mac 枚举后求并集，Windows 取虚拟桌面外接矩形；`DINF` 只传整机矩形 | 必须同时改变模型、协议、路由和界面 |

## 键盘与输入法

键盘配置应属于目标设备。用户进入 Mac 时应用 Mac 配置，返回 Windows 时应用 Windows 配置。中文组字和候选词由目标系统输入法处理，不在 Windows 先生成中文再当文字粘贴到 Mac。

Caps Lock 的中英文切换应在 Mac 上执行输入源选择，不能写死成 Command 加空格或 Control 加空格。系统快捷键可能已被用户修改；Command 加空格也可能打开 Spotlight。Apple 的输入源设置支持 Caps 在非拉丁输入源与拉丁输入源间切换，并用长按开启连续大写，但远端注入需要单独实现和验证这些语义。[Apple 输入源设置](https://support.apple.com/en-euro/guide/mac-help/mchl84525d76/mac)

本轮提供一个范围明确的 Mac 客户端选项：远端 Caps 用于切换输入源，并消费对应重复与释放事件。启用后不再让服务端的输入语言强制覆盖 Mac 的输入源。通过 macOS TIS 枚举当前可选输入源，在 ASCII 可用与非 ASCII 输入源之间选择，并在进程内记住最近使用的两者；不依赖固定快捷键。第三方输入法内部的“中文模式与英文模式”不一定对应两个系统输入源，需要单独测试。此版不实现长按开启大写；Windows 的真实 Caps 状态与键盘指示灯在返回本机后的行为仍需联机验证。GUI 保存会重启共享进程应用设置，手动修改配置文件也需要重启进程。

源端 Caps 状态可能已经影响传来的 KeyID，单纯删除 Caps 修饰位会留下大写字母。本轮应覆盖 ASCII 的 Caps 与 Shift 组合，保持命令修饰键组合的语义。其他键盘布局和非 ASCII 字符不宜用通用小写转换来猜测；完整方案应协商物理键、字符和语义动作，明确每种模式由哪端负责布局转换。

完整的目标系统习惯配置还包括：

- 用户可选择中文与英文输入源，分别保存每台设备的输入状态。
- 可选短按切输入源、长按 Caps 的状态机；断线、切屏、按键重复和组合键都有清晰的取消与释放规则。
- Ctrl、Command、Option 按目标系统配置；终端的 Ctrl+C 与常规应用的复制命令不能一概交换。
- 输入焦点会话带代号；断连或切换时释放仍按住的按键，旧会话按键不能在重连后继续生效。

## 游戏与全屏保护

把“是否允许边缘切换”独立成决策，不靠断开连接达到锁定效果。手动锁定、全屏保护和应用规则是不同原因；退出游戏只能解除自动原因，不能解除用户手动设置的锁定。

本轮新增显式启用的 Windows 全屏或鼠标捕获保护。仅在尝试离开本地 Windows 的边缘时读取平台状态，避免每个鼠标事件都扫描窗口或进程。全屏判定结合前台窗口与所属显示器的边界；`GetClipCursor` 必须与完整虚拟桌面范围比较，不能把正常的未裁剪范围当作应用捕获。[Microsoft GetClipCursor](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipcursor)

全屏视频也可能触发保护，第一版必须这样命名和说明。后续再增加按应用的“禁止离开、允许离开、继承全局”规则，以及前台变化通知和短暂去抖。单一 Direct3D 全屏标志不能覆盖所有无边框游戏。

自动保护只阻止边缘切换，用户配置的主动跳转快捷键可越过自动保护；已有手动锁定语义保持独立。延迟切屏定时器到期时必须重新检查状态，避免鼠标碰边后恰好打开游戏仍然切出去。游戏启动时若光标已经在 Mac，不应无提示抢回输入焦点。

## 独立的控制与数据通道

```text
已经认证的设备会话
├── 控制连接 TLS/TCP
│   ├── 键鼠事件与输入焦点
│   ├── 能力协商与显示器拓扑
│   └── 音频路由和文件任务控制
├── 音频传输
│   └── 独立连接、有界队列、音频时间戳、过期帧处理
└── 文件连接 TLS/TCP
    └── 按块读写、断点恢复、校验、带宽预算
```

同一 TCP 字节流内的分队列不能消除重传时的队头阻塞。新增音频与文件不能继续挤在键鼠的字节流上。独立连接仍共享真实网络带宽，文件传输必须按拥塞和输入延迟退让，给控制与音频保留余量。

使用有界队列和可取消任务。输入回调不等待磁盘、编码器、文件哈希或音频设备。显示器与策略变化生成新的只读快照，输入路径只查当前快照。队列满时的动作必须按业务定义：文件等待可用窗口，晚到音频丢弃并恢复，按键抬起与焦点状态不能随意丢弃。

能力协商应包含功能及版本，例如 `display-topology/1`、`file-copy/1`、`audio-output/1`，以及格式、传输方式和上限。先在兼容握手中确认双方理解扩展，再发送新消息；不能把未知消息直接发给旧解析器。旧端继续使用现有矩形与键鼠协议。

## Windows 声音到 Mac

推荐固定路由“Windows 系统输出 → Mac 的耳机或扬声器”，默认不随鼠标移动。游戏保护开启时声音继续播放。第一版按用户开关镜像播放，本机静音而远端继续正常播放需要单独验证端点与音量行为，不能直接通过全局静音假定能够实现。

```text
WASAPI shared-mode loopback
  → 采样格式与声道转换
  → Opus 编码
  → 独立的加密音频传输
  → 抖动缓冲、解码、时钟漂移修正
  → 有界 PCM 环形缓冲
  → Mac 输出设备
```

WASAPI loopback 能从播放端点取得系统混音，无需把麦克风当作系统声音，也不要求用户先开启硬件 Stereo Mix。Windows 10 1703 起支持事件驱动 loopback；这是 shared-mode 能力，独占模式和受保护内容需按实际源端条件验证。[Microsoft Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)

初期用独立 TLS/TCP 连接验证真实采集和播放链路；低延迟生产实现再选成熟的安全数据报方案，例如 QUIC DATAGRAM 或 RTP/SRTP。该选择应经过依赖、跨平台构建、网络退化与资源占用评估，避免自造未认证 UDP 协议。

Opus 先使用 48 kHz 双声道、20 ms 帧、128 至 192 kbps 有效编码带宽，随后用测量调整。48 kHz 双声道 16 bit PCM 的有效载荷是 1.536 Mbps；这只是算术对比，不代表编码后完整链路开销或延迟已经测得。

播放端可先保留 QAudioSink。格式不支持时必须转换或拒绝，不能改用设备 preferredFormat 后继续写原格式字节。正确处理部分写入、启动失败、设备变更和欠载。缓冲容量不是端到端延迟；应读取实际设备缓冲并测量。仓库最低 Qt 6.7，不直接使用 Qt 6.11 才出现的回调接口。[Qt QAudioSink](https://doc.qt.io/qt-6/qaudiosink.html)

两端声卡时钟有微小差异，持续播放需根据缓冲占用调整重采样，否则固定缓冲迟早溢出或欠载。音频帧包含流代号、序号与源采样时间戳；重连和换设备必须开始新流，不能播放旧积压声音。

本轮修复的是已有测试音原型：握手完成后配置，接收端确认 ready 后才发送，默认关闭测试音，并对格式与播放失败做明确处理。测试需要两端 core 进程环境都设置 `DESKFLOW_AUDIO_TEST_TONE=1`，仅用于开发者验证 440 Hz 合成音管线。此原型仍共用控制连接，部分写入时安全停流；它不包含 WASAPI 系统音频采集、Opus、独立媒体通道或生产级恢复。

## 文件复制与跨桌面拖放

产品先完成双向文件与文件夹复制，再增加拖放。源文件始终保留；跨机剪切涉及接收成功确认和删除事务，作为后续独立能力设计。

```text
复制文件
  → 发布文件清单与剪贴板代次
  → 目标端取用
  → 独立连接分块传输
  → 临时文件校验并完成
  → 目标端原生文件对象或传输栏
```

Windows 的 CF_HDROP 是实际本地文件路径列表，不能把 `C:\\...` 发到 Mac 就完成共享。Windows 虚拟文件使用 FILEDESCRIPTOR 与 FILECONTENTS，内容可通过 IStream 提供。[Microsoft Shell clipboard formats](https://learn.microsoft.com/en-us/windows/win32/shell/clipboard)

Mac 的文件承诺适合拖放延迟交付，但 NSFilePromiseProvider 本身不证明 Finder 和任意应用都能通过普通 Command+V 取远端文件。应分别验证原生剪贴板与拖放；不支持延迟粘贴的路径可先下载到受管理缓存，再发布真实本地文件 URL，并提供传输栏作为可靠入口。[Apple 文件承诺示例](https://developer.apple.com/documentation/appkit/supporting-table-view-drag-and-drop-through-file-promises)

原型首先验证 Explorer 与 Finder 双向复制粘贴，随后覆盖文件管理器、聊天附件框和常用编辑器。跨桌面拖放包含源端拖动状态、目标原生拖放会话和失败回退，不能仅把鼠标轨迹跨过去。

传输服务的基本要求：

- 传输清单使用对象 ID，接收端只能请求本次选择的对象；源路径留在源设备。
- 按块流式读写和计算校验，内存随并发窗口增长，不随文件总大小增长。
- 接收端写临时文件，完成校验后再提交；处理重名、磁盘满、取消、断线和源文件传输中变更。
- 对目录路径做规范化，明确大小写重名、保留字符、符号链接、包目录和元数据策略；普通文件先实现，复杂语义不能静默损坏。
- 断点恢复必须确认源文件版本未变。后续复制文字不应改变已经开始的文件任务。
- 进度、取消和失败原因在传输栏可见；清单就绪与传输完成是不同状态。

## 每块显示器独立布局

```text
Device
  └── Display
      ├── persistentId
      ├── nativeRect / scale / rotation / primary
      └── Portal
          ├── sourceDisplay / sourceEdge / sourceInterval
          └── targetDisplay / targetEdge / targetInterval
```

Device 是连接和资源所有者，Display 是鼠标可到达的显示表面，Portal 是两块屏幕之间开放的边缘区间。画布位置与原生坐标分开保存；用户在 Deskflow 中调整布局不应擅自改变 Windows 或 macOS 的系统显示设置。

每块显示器独立拖动、吸附、识别编号。用户可以只开放某段边缘，支持竖屏、上下错位和不同缩放；显示器颜色或标签标识所属电脑。跨屏时先确定目标显示器，再根据边缘归一化位置映射到其本地坐标。

验收必须包含 `Windows 1 → Mac 1 → Windows 2`。即使 Windows 的两块屏幕在系统中相邻，也要能在其内部接缝处设置到 Mac 的入口。仅拆分 UI 图块而仍以整机外接矩形判边缘，无法实现这一布局。

新拓扑消息需包含有符号 32 位坐标、稳定显示器身份、缩放、旋转和拓扑版本。运行时 display ID 可能随热插拔改变，需结合平台持久 ID，并处理相同显示器与无 EDID 情况。镜像显示器折叠为一个逻辑目标。

热插拔重建不可变拓扑快照，保留仍存在屏幕的用户位置，禁用断开的入口，并把光标退回有效位置。带旧拓扑版本的切换请求重新映射或拒绝，不能注入到不存在的屏幕。

旧客户端继续上报 DINF 外接矩形，旧网格迁移成设备整体布局。双方协商拓扑能力后才能使用每屏路由；用户应能看见某台旧设备暂时只支持整体摆放。

## 交付顺序与验收

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| 本轮 | Mac Caps 可选模式、Windows 边缘保护、音频原型正确性修复、设计文档 | 本机编译及相关自动测试通过；联机限制逐项说明 |

| 项目 | 初始验收目标或方法 |
